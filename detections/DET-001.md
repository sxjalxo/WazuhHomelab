## 1. Problem statement and original detection gap

INC-001 produced three kinds of alert for one SSH connection from Kali (`192.168.56.105`). Only the level-10 alert had no structured source IP:

| Rule | Level | Decoder | `data.srcip` |
|---|---|---|---|
| 5710 | 5 | `sshd` | yes |
| 5503 | 5 | `pam` | yes |
| **2502** | **10** | `sshd` | **no** |

The IP was in the log line (`rhost=192.168.56.105`), but nothing extracted it. As a result:

- A pivot on `data.srcip:192.168.56.105` returned the two level-5 alerts and **missed the most severe alert of the session**.
- No correlation keyed on `srcip` could use 2502. That includes a planned frequency rule and active response.

**Goal:** extract `rhost` as `srcip` on this line without changing which rule fires or its severity.

### Why no stock decoder extracted it (Verified)

| Stock decoder | Requirement | Result for the INC-001 line |
|---|---|---|
| `pam` (`0205-pam_decoders.xml`), whose `pam-fields` child extracts `rhost` → `srcip` | Program name ending `(pam_unix)`, or a message starting `pam_unix` / `(pam_unix)` | No match: the message starts `PAM 2 more…` |
| `sshd-pam-host-user` (`0310-ssh_decoders.xml`) | Prematch `rhost=\S+\s+user=\S+` | No match: the line **ends at `rhost=…`**, with no `user=` field |

Source: E-29 §2–3.

The endpoint shows when the `user=` field appears (E-32, E-33):

| Target account | PAM summary line ends with | Decoded by | Fields on the 2502 alert |
|---|---|---|---|
| Non-existent (`invaliduser`) | `rhost=192.168.56.105` | parent `sshd` only (before DET-001) | none |
| Existing (`ubuntu`) | `rhost=192.168.56.105  user=ubuntu` | stock `sshd-pam-host-user` | `srcip`, `dstuser` |

**The gap was specific to attempts against non-existent accounts.** Failures against a real account were already attributed by the stock ruleset. That makes the gap more serious, not less: invalid-username guessing is the more typical pattern for an outside attacker, and that is exactly the case that lost its source IP.

## 4. Decoder implementation

### Current version (v2, Verified)

```xml
<decoder name="sshd-pam-auth-failures">
    <parent>sshd</parent>
    <prematch>PAM \d+ more authentication failure</prematch>
    <regex>rhost=(\S+)</regex>
    <order>srcip</order>
</decoder>
```

| Element | Purpose |
|---|---|
| `<parent>sshd</parent>` | Evaluated only for lines the built-in `sshd` decoder has claimed. PAM lines from other programs are out of scope. |
| `<prematch>PAM \d+ more authentication failure</prematch>` | Selects sshd's PAM summary line in both wordings: `… failure;` (one more) and `… failures;` (two or more). `\d+` covers any count. |
| `<regex>rhost=(\S+)</regex>` | Captures the token after `rhost=`. Unlike `sshd-pam-host-user`, it does not require a `user=` field. |
| `<order>srcip</order>` | Stores the capture as `srcip`, the same field rules 5710/5503 and DQL pivots use. |

It sits in `local_decoder.xml` after Wazuh's stock header comment and `local_decoder_example`, confirmed by `cat` at 19:13 with a clean `wazuh-analysisd -t` (E-36 §1). The stock `ruleset/decoders/` files are not edited.

## 8. Finding: sessions with exactly two failures produce no session-level alert

During testing, the operator fed the singular wording into `wazuh-logtest` with **v1** in place (E-31 §3). The line was synthetic, built from the INC-001 line:

```text
Nov 10 00:00:00 ubuntu sshd[3001]: PAM 1 more authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=192.168.56.105
```

```text
**Phase 2: Completed decoding.
        name: 'sshd'

**Phase 3: Completed filtering (rules).
        id: '5711'
        level: '0'
        description: 'sshd: Useless/Duplicated SSHD message without a user/ip.'
```

What this shows (**Verified** in logtest):

1. **v1 did not decode it.** Its prematch ended at `failures;`.
2. **Rule 2502 did not match it either.** The plural and singular lines decoded identically (`name: 'sshd'`, no fields), yet only the plural matched 2502. 2502's condition therefore depends on the plural wording in the text.
3. **The line produces no alert at all.** It falls to rule 5711, level 0. The manager uses `log_alert_level 3` with `logall` off ([architecture](../docs/architecture.md)), so a level-0 match is neither alerted nor archived.

**Impact:** if sshd writes the singular form for a connection with exactly two failed passwords, that connection gets no session-level alert. The per-attempt alerts (5710, 5503) still fire. Whether sshd on this endpoint actually writes the singular form has **not been observed**: every captured session had three failures.

**v2 response (Verified, E-36 §2).** The operator widened the prematch to `… authentication failure` (v2) and re-ran the same line:

```text
**Phase 2: Completed decoding.
        name: 'sshd'
        parent: 'sshd'
        srcip: '192.168.56.105'

**Phase 3: Completed filtering (rules).
        id: '5711'
        level: '0'
        description: 'sshd: Useless/Duplicated SSHD message without a user/ip.'
```

- **v2 decodes the line.** `srcip` is now extracted.
- **The rule outcome is unchanged:** still 5711 at level 0, with no `Alert to be generated`. Rule 5711 matched even though the event now carries an IP, so it does not check decoded fields, despite its description.
- **Correction:** an earlier draft recorded, from the operator's account, that the singular line "produced an alert" under v2. The captured logtest output shows it does not, and that statement is withdrawn.

**Conclusion:** the decoder alone cannot close this gap. v2 is groundwork: the `srcip` it extracts becomes useful once a rule raises the line above `log_alert_level`. A sketch of such a rule follows. It is **not deployed and not tested**:

```xml
<!-- /var/ossec/etc/rules/local_rules.xml : sketch only -->
<group name="local,syslog,sshd,">
  <rule id="100100" level="5">
    <if_sid>5711</if_sid>
    <match>PAM 1 more authentication failure;</match>
    <description>sshd: two failed passwords in one session (PAM summary)</description>
    <group>authentication_failed,</group>
  </rule>
</group>
```

The level and any MITRE mapping should be chosen deliberately, then tested with `wazuh-logtest` and a live two-attempt session before deployment. Track this as its own detection.

## 10. Limitations and validation scope

**Tested:**
- Non-existent-account summary lines: IPv4 `rhost`, plural wording (three failures), on Ubuntu 24.04.5 / OpenSSH 9.6p1 via `journald`, Wazuh 4.14.10.
- One live session per account type.

**Not tested:**
- **Two-failure sessions:** no alert (§8). The singular wording is also not yet observed live.
- **Other `rhost` values.**
  - IPv6 is untested.
  - With `UseDNS yes`, `rhost` may be a hostname, and `\S+` would store it in `srcip`.
  - An empty `rhost=` is untested.
- **Other services.** PAM summary lines from other programs are out of scope by design.

**Unchanged by DET-001:**
- **No username for non-existent accounts.** The summary line has empty `logname=`/`ruser=` and no `user=`, so it carries no username. The attempted name is on the 5710 alert for the same sshd PID.
- **Detection logic.** 2502 still fires on one end-of-session line, not on a pattern across connections. Its T1110 tag remains rule metadata. DET-001 improves pivoting and correlation, not detection.
- **Past alerts.** Already-indexed alerts, including INC-001's E-18, keep no `srcip`.

**Upgrade persistence:**
- Whether `local_decoder.xml` survives a Wazuh upgrade was not tested.
