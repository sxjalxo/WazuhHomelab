## 1. Problem statement

sshd writes one PAM summary line when a connection that had more than one failed password closes. Rule 2502 (level 10) alerts on it, but only in its plural form. When a session ends after **exactly two** failures, the line uses the singular form. DET-001 §8 showed in `wazuh-logtest` that this singular line matches rule 5711 at level 0. The manager uses `log_alert_level 3` with `logall` off, so that event is neither alerted nor archived.

The per-attempt alerts (5710, 5503) still fire for each failure. What was missing is the session-level summary, so a two-failure session never reached the same view as a three-failure one.

**Goal:** raise the singular summary line to an alert, without changing how any other sshd message is handled.

## 2. The gap occurs on the live system (Verified)

From Kali, two wrong passwords for a non-existent account were entered, then the client was closed with Ctrl+C at the third prompt (E-37). The endpoint recorded the session as sshd PID 2566 (E-38):

| Time (UTC) | Line |
|---|---|
| 10:23:01.942 | `Invalid user invaliduser from 192.168.56.105 port 52958` |
| 10:23:07.604 | `pam_unix … check pass; user unknown` / `pam_unix … authentication failure; … rhost=192.168.56.105` |
| 10:23:09.453 | `Failed password for invalid user invaliduser …` (1) |
| 10:23:13.100 / 10:23:15.439 | `check pass; user unknown` / `Failed password …` (2) |
| 10:23:17.564 | `Connection closed by invalid user invaliduser 192.168.56.105 port 52958 [preauth]` |
| **10:23:17.564** | **`PAM 1 more authentication failure; logname= uid=0 euid=0 tty=ssh ruser= rhost=192.168.56.105`** |

This confirms that the singular wording occurs. Until now, DET-001 had only tested it as a synthetic logtest input.

The other sshd lines in E-38 are not part of the test:
- PID 693 is the sshd service starting at boot.
- PID 2084 (`Accepted password for ubuntu from 192.168.56.1`) is the operator's admin session from the Windows host. Running admin sessions from the host keeps attack traffic and admin traffic on different source IPs, as the roadmap recommends.

## 3. Root cause from the rule source (Verified, E-39 §2)

```xml
<rule id="2502" level="10">
  <match>more authentication failures;|REPEATED login failures</match>
  …
<rule id="5711" level="0">
  <if_sid>5700</if_sid>
  <match>authentication failure; logname= uid=0 euid=0 tty=ssh|</match>
  …
  <description>sshd: Useless/Duplicated SSHD message without a user/ip.</description>
```

| Line | Contains `more authentication failures;` (2502) | Contains `authentication failure; logname= uid=0 euid=0 tty=ssh` (5711) | Result |
|---|---|---|---|
| `PAM 2 more authentication failures; logname= uid=0 euid=0 tty=ssh …` | yes | no (`failures;`, not `failure;`) | 2502, level 10 |
| `PAM 1 more authentication failure; logname= uid=0 euid=0 tty=ssh …` | no | **yes** | 5711, level 0, no alert |

Two things follow from this:

- **2502 is a plain text match.** It has no `if_sid` and no decoder condition, so field extraction (DET-001) cannot change whether it fires. This confirms the inference in DET-001 §3 and §8.
- **5711's description doesn't fit this line.** It says "without a user/ip", yet it is a text match too, so it catches the singular summary line even though that line has an `rhost`. This is how a two-failure session gets filed as a "useless/duplicated" message.

## 4. Rule implementation

Deployed in `local_rules.xml` as a second group after Wazuh's stock example group (rule `100001`), confirmed by `cat` after the live test (E-39 §8). The deployed copy also carries a short DET-003 comment inside the group. The repository copy is [`rules/local_rules.xml`](rules/local_rules.xml):

```xml
<group name="local,syslog,sshd,">
  <rule id="100100" level="5">
    <if_sid>5711</if_sid>
    <match>PAM 1 more authentication failure;</match>
    <description>sshd: two failed passwords in one session (PAM summary)</description>
    <mitre>
      <id>T1110.001</id>
    </mitre>
    <group>authentication_failed,</group>
  </rule>
</group>
```

| Choice | Reason |
|---|---|
| `if_sid 5711` | The rule is evaluated only after 5711 has matched, so it cannot affect any other sshd message. 5711's other matches stay at level 0. |
| `match PAM 1 more authentication failure;` | Selects only the singular summary line from among 5711's matches. |
| Level 5 | Same as the per-attempt alerts (5710, 5503) and below 2502's level 10. Two typos in one session is common for a real user, so the alert is visible but not loud. |
| `authentication_failed` group | Puts the alert in the same dashboard panels and group queries as the related rules. |
| MITRE T1110.001 | Rule metadata naming the technique this line *could* indicate, consistent with 5710/5503. It is not evidence that password guessing took place. |
| ID 100100 | In the custom range (100000–120000); the only existing local rule is the stock example 100001 (E-39 §1). |

`srcip` on the alert comes from the DET-001 decoder. Without DET-001 v2, this rule would still fire, but the alert would carry no source IP.

## 8. Limitations and validation scope

**Tested:**
- The non-existent-account form of the singular line: in logtest, and in one live session.

**Not tested:**
- **Real-account two-failure sessions.** Their singular line should end in `rhost=…  user=<name>`. It still contains 5711's match text and this rule's match text, so it should reach 100100, with `dstuser` from the stock decoder. This is untested.

**Dependencies:**
- **Rule 5711.** If a Wazuh update changes 5711's match text or ID, this child rule stops matching. Re-run T1 after upgrades.

**What it does not do:**
- **No correlation.** Like 2502, this rule fires once per SSH connection. It does not correlate across connections; that is DET-002 on the [roadmap](../docs/roadmap.md).
- **No single-failure summary.** A session with only one failed password produces no PAM summary line, so it is covered only by the per-attempt alerts.

**Judgement call:**
- **Level 5 is a choice, not a measurement.** Revisit it once baseline noise from legitimate logins is known.
